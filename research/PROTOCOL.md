# MT760L protocol notes

Version note: these are historical evidence notes. The original Mac and Windows packages were hardware-tested. Version 0.2.0 removes fixed-line scrolling and adds native desktop windows and a polling selector; see `POLLING-RATE.md` and current development docs for the active implementation.

Confidence labels: **observed** means bytes directly present in the capture; **static inference** means backed by DLL code but not hardware-tested; **unknown** means it must not be represented as a confirmed feature.

## Live receiver inspection — 2026-10-30

The supported 2.4 GHz receiver enumerates as **Rapoo Gaming Device, VID 24ae / PID 1870**. Its mouse interface has only a 7-byte input report. A second HID interface has keyboard primary usage (01:06) and five top-level collections, including **ff00:000e with input/output report BA, 248 payload bits each**. Another ff00:0002 collection uses BB with 48 payload bits. A third ff01:0000 interface uses report 06 with 224 payload bits, including feature support; it is not the captured BA transport.

This verifies the original 32-byte BA framing. It also explains why assuming a separately exposed vendor HID interface was insufficient. macOS marks the keyboard+vendor interface as requiring TCC authorization. Direct IOKit enumeration through portable Node FFI succeeds. Initial standalone IOHIDDeviceOpen probes returned **0xe00002e2 (not permitted)**, including outside the execution sandbox; the updated running app later **opened the receiver successfully**, verified by its device card and CONNECTED entry. No configuration reports were sent during verification. Live writes remain unverified. The bridge never registers general keyboard/mouse input callbacks.

The real descriptor strings are fixtures in `app/test/hid-descriptor.test.mjs`. Earlier capture-only statements below describe the supplied PCAPNG, not the newly observed USB identity. The Mac bridge loads only OS frameworks via [Node 26.4 FFI](https://nodejs.org/download/release/v26.4.0/docs/api/ffi.html); no tool installation or compilation was used.

## Inputs

- `rapoo-re/rapoo_760l_config.pcapng`: 9,200 bytes, PCAPNG with USBPcap link type 249. 107 enhanced-packet records, all host-side submissions. No returned device/configuration descriptors or device response bytes. The filename says `760l`; the recorded mouse model is **Rapoo MT760L**, with DPI changes and a button action change. Connection type was not explicitly confirmed.
- `rapoo-re/RapooDevice.dll`: 32-bit Windows PE DLL, image base `0x6fd00000`, with exported C++ names and HID calls. Not executed.
- `rapoo-re/A HUB.exe`: Windows vendor app; not executed.

Hashes and export inventory are generated by `scripts/evidence.mjs`.

## USB transport — observed

SET_REPORT: `bmRequestType=0x21`, `bRequest=0x09`, `wValue=0x02ba`, `wIndex=1`, `wLength=32`. This is **Output report BA**, not a feature report. GET_REPORT requests use `bmRequestType=0xa1`, `bRequest=0x01`, `wValue=0x01ba`, interface 1, length 32: **Input report BA**. There are repeated GET_REPORT attempts after some output requests. No completions are present, so actual responses, success status and retry behavior cannot be inferred.

The PCAP parser follows the [USBPcap format specification](https://desowin.org/usbpcap/captureformat.html): 27-byte base pseudoheader, control stage at byte 27, payload at the header-length offset, and eight setup bytes before outgoing control data. The request/completion info bit is separate from endpoint direction. Endpoint `0x80` on these GET_REPORT submissions does not mean captured response data exists.

WebHID's `sendReport(0xba, fullReport.slice(1))` is the corresponding output operation. [Chrome's WebHID documentation](https://developer.chrome.com/docs/capabilities/hid) describes separate output/feature APIs and browser blocking of protected mouse/keyboard collections. Only a compatible exposed vendor collection is accepted by this app. [The WebHID interface specification](https://wicg.github.io/webhid/#hiddevice-interface) exposes input events and feature reads, but no explicit GET_REPORT(Input) operation. Input events are logged unparsed; they are not treated as polling responses.

## Full report layout

Offsets include the report ID:

| Offset | Value / meaning | Confidence |
| --- | --- | --- |
| 0 | `ba`, HID report ID | observed |
| 1 | `a5`, command marker for parameter traffic | observed |
| 2 | `a4` in read commands, `a5` in parameter writes | observed; operation semantics inferred from sequencing |
| 3 | Parameter byte length (`04`, `08`, `10`, `14`, `18`) | observed; length semantics static inference |
| 4–7 | Little-endian parameter address | static inference consistent with capture |
| 8 onward | Parameter bytes / zero padding | observed |

Other reports (`ba a5 a3...`, `ba b0...`) occur but are not exposed as replay actions.

## DPI block — static inference, supported by captures

Writes at address **0x0638**, byte length `0x14` (20):

| Full-report bytes | Meaning |
| --- | --- |
| 8–19 | Six little-endian 16-bit DPI values, each multiplied by 50 for UI DPI |
| 20–21 | Unknown; preserved from template |
| 22 | Enabled stage count minus 1 |
| 23 | Unknown; preserved |
| 24 | Current stage index minus 1 |
| 25–27 | Other configuration fields; preserved |
| 28–31 | Padding, preserved |

| Frame | Six DPI slots | Enabled count | Active stage |
| --- | --- | --- | --- |
| 12 | 800, 1000, 1200, 1700, 3200, 4000 | 6 | 4 |
| 16 | 800, 1000, 1200, 1700, 4000, 0 | 5 | 4 |
| 20 | 800, 1000, 1200, 1700, 4000, 800 | 6 | 4 |
| 28 | 800, 1000, 1200, 1700, 4000, 1600 | 6 | 6 |

The app bounds nonzero values to 50–4000, step 50 as an experimental editing limit, **not a discovered hardware capability range**. It accepts zero only in disabled slots. It uses frame 12 initially and allows loading other DPI capture templates. The current mouse's settings may differ from every template.

Frame 24 writes `05 00 03 02` at **0x0648**, a nearby configuration block. Its full meaning and whether a follow-up write is needed for every DPI edit remain unknown. The app doesn't silently send it after DPI writes.

## Other writes

- Frames 40/44/48/52/56 at **0x0630**: `01 01 ff ff`, `04 04 ff ff`, `08 08 ff ff`, `01 01 ff ff`, `08 08 ff ff`. Static code treats this as another parameter block. No named behavior is asserted.
- Frames 104/106 at **0x0610**: `09 00 01 00` and `08 00 03 00`. Candidate button-assignment records, consistent with the recorded button edit and the surrounding 0x0600…0x0628 address range. Physical button and action names remain unknown. The app can inspect/preview/replay these exact captured reports.
- Read commands cover 0x0600…0x0628, 0x0630, 0x0648, 0x08d8, and 0x1000…0xc000. Their requests alone cannot establish the returned data layout.

## DLL landmarks for continued analysis

Addresses below are **virtual addresses in this exact DLL**, not file offsets. Nearby symbol labels emitted by objdump are often just the nearest exported symbol: they must not be mistaken for the actual identity of unexported functions.

- `.rdata` RVA `0x2ab000`, raw offset `0x2a8800`. For strings within that section, VA = file offset + `0x6fd02800`.
- `DeviceFactory::getDevice` at `0x6fd9d090`: compares string `MT760` at `0x6ffb3274` and `MT760 Mini`; branch around `0x6fd9dcde` constructs a device using function `0x6feafcd0`. This proves a MT760-family branch, not the MT760L USB identity.
- Constructor `0x6feafcd0`, around `0x6feafd39–0x6feafded`: initializes address fields to `0x600, 0x604, …, 0x628, 0x630, 0x634, 0x638, 0x646, 0x648, 0x64c, …`. Address 0x638 is at object offset 0x360, 0x648 at 0x368.
- DPI writer around `0x6feb2530`: loads address field 0x360; sets block length `0x14`; looks up strings `DPIListX` (VA `0x6ffc1c03`), `CurDpiGear` (`0x6ffc1c0c`), `Size` (`0x6ffc1c17`).
- `0x6feb2720–0x6feb274a`: converts list values by signed divide-by-50 (multiply by `0x51eb851f`, shift and sign correction), stores low/high bytes at object offset `0xa1 + 2*i`.
- `0x6feb2766–0x6feb27a9`: stores `Size - 1` at object 0xaf and `CurDpiGear - 1` at 0xb1. Parameter bytes begin at object 0xa1; the USB packet includes eight header bytes before parameter data, giving full-report offsets 22 and 24.
- `0x6feb54b0` loads fields 0x368 and 0x36c for nearby current-DPI/configuration reads. Return layout still needs response evidence.
- Imports include `HidD_SetOutputReport`, `HidD_GetInputReport`, `HidD_SetFeature`, and `HidD_GetFeature`. The presence of feature APIs elsewhere in the DLL does not change this capture's report type.

Generated disassembly is at `research/generated/RapooDevice.disassembly.txt`. It was produced with the Mac's existing `objdump -d --x86-asm-syntax=intel`. Focused excerpts can be regenerated by `scripts/evidence.mjs` when that disassembly exists.
